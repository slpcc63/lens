# Release procedure

The only release input is **`dist/sniffies.user.js`**, generated by `python3 work/build.py`. `VERSION` controls userscript metadata, Chrome manifest/popup and runtime version labels. The root script is a compatibility copy. The Doxle icons are owner-confirmed distributable; no general open-source license has been selected by this change.

1. Make scoped changes on a review branch, increase `VERSION` to a new stable major.minor.patch value, update `docs/RELEASE-NOTES.md`, run the build and all commands in README, and commit the generated outputs. Never hand-edit the release artifact or reuse a published version/tag.
2. Review the diff and record automated evidence. Complete the versioned Safari/device QA request for the exact artifact; do not treat local unit tests as installation or owner acceptance. Obtain Shannon's approval for the exact release and record it in the source chat. No release publication is currently authorized.
3. Merge the reviewed code into `main`. Only after explicit authorization to create the release tag, tag the approved commit `vVERSION` and push that tag. Tags alone do not run the draft workflow.
4. In GitHub → Actions → **Prepare draft release (never publishes)** → **Run workflow**, select **main** and enter the existing tag. The workflow requires a stable version/tag match, a tag in main's history, a committed artifact, passing tests and no regenerated diff. It uploads exactly `dist/sniffies.user.js` under asset name **sniffies.user.js**, creating a new **draft**. It refuses existing releases and never edits assets or publishes. Failed requests require inspection before manual rerun; there is no automatic retry.
5. Inspect the draft's version, tag commit, release notes and asset SHA-256 against `python3 work/validate_release.py --tag vVERSION`. Keep it a draft until the exact release is approved. Source/QA preview URLs can test the bytes without publishing; they do not prove the GitHub release redirect works on Safari.
6. Once explicitly approved, a maintainer can use the draft's **Publish release** control. Mark it the latest stable release, not a prerelease. This is a separate human approval/action, never a CI consequence. Do not move old tags or overwrite old assets.
7. Verify the stable URL redirects to the expected asset, inspect the metadata version and compare SHA-256. Perform the final Safari delivery check, then check a lower installed version with **Check Updates → Update**. If release delivery fails, retain the working installed version and investigate; do not claim completion. An attachment-only Safari response may require a separately reviewed hosting adjustment.

The stable channel is GitHub's latest published stable release, independent of development branches and draft releases. Archived fixed-tag assets preserve rollback; native comparison rejects downgrades, so use explicit reinstall/backup restore. Removing a bad release from latest is a separate authorized operation and does not downgrade existing installs.

This workflow does not install runtime loaders, add paid services or modify storage keys. It preserves installed execution when update hosting fails because no network dependency is added to startup. Actual offline/device behavior must still be tested.
